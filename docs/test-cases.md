# Тест-кейсы

Ручные и автоматические проверки сервиса задач креативного отдела. Кейсы составили два независимых аудитора, которые не видели код:

- **Часть A — по заданию.** Аудитор шёл по ТЗ и `docs/decisions.md`: роли, машина состояний, учёт времени, просрочки, AI-расходы, аналитика, демо-стенд. ID вида `ТЗ-<раздел>-NN`.
- **Часть B — по практикам канбан-досок.** Эксперт по UX сравнивал доску с Trello, Jira, Linear, YouTrack, GitHub Projects и WCAG 2.2: перетаскивание, карточка, фильтры, синхронизация, адаптивность, доступность. ID вида `KB-<раздел>-NN`.

После этого каждый кейс сверен с реализацией и автотестами. Результат — в колонке «Покрытие».

Тестовые пользователи (пароль `demo12345`): **head** — руководитель; **anna**, **dmitry** — байеры; **ivan**, **maria**, **sergey** — креативщики; **kate** — байер и креативщик. В части B роли обозначены условно: Б1/Б2 — байеры, К1/К2 — креативщики, Р — руководитель, БК — байер-креативщик (kate).

## Обозначения

**Приоритет:** P1 — без этого сервисом нельзя пользоваться; P2 — важно; P3 — желательно.

**Покрытие:**

| Знак | Значение |
|---|---|
| ✅ | Реализовано и проверяется автотестом |
| 🟢 | Реализовано, проверка вручную (Р) |
| 🟡 | Реализовано частично или иначе, чем ожидает кейс |
| 🔴 | Не реализовано |

**Где лежат автотесты:** B — backend, pytest (`backend/tests/`, имя функции `test_…`); F — frontend, Vitest (`frontend/src/**/*.test.ts(x)`, имя файла и текст `it(…)`); E — Playwright (`e2e/tests/`). Р — ручная проверка.

**PW** — разовый прогон Playwright по ручным кейсам 09.11.2026 (34 проверки, локальный стенд): ✓ — поведение подтверждено, ✗ — расхождение подтверждено.

## Неоднозначности ТЗ, найденные аудитором

Как они решены в реализации:

1. **Время при смене исполнителя и возврате в пул.** Каждому исполнителю засчитываются его отрезки работы, время задачи — их сумма; время в пуле не считается (ТЗ-TIME-06, ТЗ-TIME-07). Расходы на AI идут автору записи. Прежний исполнитель после смены свои записи не добавляет.
2. **AI-расходы на правках.** Учитываются без разбивки по этапам: правки входят в общий итог задачи.
3. **Кого можно назначить исполнителем.** Только активного креативщика, не автора задачи и не текущего исполнителя (ТЗ-FLOW-15). Руководитель без роли креативщика не назначается.
4. **Граница просрочки.** Опоздание — только если первая сдача строго позже дедлайна. Как в аналитике учитываются отменённые просроченные задачи, нужно явно записать в `docs/decisions.md` (ТЗ-OVER-08).
5. **Расхождения ТЗ с решениями** (руководитель тоже принимает работу, дедлайн необязателен, статус «Отменена» вне доски) — осознанные, обоснованы в `docs/decisions.md`. Пометка «ТЗ изменено» снимается при новом взятии задачи, а не при просмотре (ТЗ-FLOW-19).
