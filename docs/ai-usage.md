# Журнал использования AI-инструментов

Ведётся по ходу работы, по этапам. Итоговое описание для README собирается из этого журнала на этапе 10.

## Инструменты

- **Claude Code** (CLI) — основной агент: разбор ТЗ (Claude Haiku 5.5), проектирование, код backend и frontend, тесты, документация (Claude Opus 5.5).
- **Субагенты Claude Code** — независимый аудит изменений этапа (агент получает diff и спецификацию, но не рассуждения основного агента).

## Подготовка (до кода)

- Разбор ТЗ: агент составил список неоднозначностей (22 вопроса) с вариантом по умолчанию для каждого.
- Все вопросы разобраны с человеком по одному; решения зафиксированы в документе решений, из него собран поэтапный план (этапы 0–10).
- Порядок на каждом этапе: реализация → рефакторинг → аудит (находки записываются до исправлений) → исправления → полный прогон тестов → коммит.

## Этап 0. Каркас

- Агент: структура монорепо, Docker Compose, FastAPI + Alembic, React + Vite + Mantine, CI.
- Вручную проверено: подъём стенда `docker compose up --build`, health через nginx, прогон линтеров и тестов.

## Этап 1. Пользователи, роли, аутентификация

- Агент: модели и миграция, JWT в httpOnly-куке с версией токена, демо-вход, управление пользователями, экран входа и layout.
- Аудит агента нашёл: неограниченный рост памяти у ограничителя попыток входа, английские ошибки валидации — исправлено, покрыто тестами.
- Визуальная проверка — скриншоты Playwright (headless Chrome), просмотренные агентом.

## Этап 2. Задачи и машина состояний

- Агент: модели задач, истории и отрезков работы; единый модуль правил доступа (и проверка, и список доступных действий для UI); переходы с блокировкой строки.
- **Независимый аудит — отдельный субагент.** Получил только код и спецификацию (без рассуждений основного агента), запускал тесты и `alembic check`. Нашёл 6 проблем, главная — перенос дедлайна после сдачи стирал просрочку; плюс пробелы в тестах. Всё исправлено, добавлено 22 теста.

## Этап 3. Файлы и ссылки

- Агент: хранилище за интерфейсом `FileStorage`, определение типа по сигнатуре, безопасная отдача файлов, версии результатов по кругам правок, сдача только с результатом.
- Аудит (основной агент): запрет удалять уже сданный результат прошлого круга — исправлено, покрыто тестом.

## Этап 4. AI-расходы

- Агент: справочник сервисов (уникальность без учёта регистра на уровне индекса БД), расходы по задаче с итогами по каждому сервису, страница справочника.
- Аудит (основной агент): гонка параллельного удаления одной записи давала 500 — исправлено, тест с двумя одновременными запросами.

## Этап 5. Фронт: доска и карточка задачи

- Агент: канбан с drag-and-drop (разрешённые колонки — по списку действий от backend), карточка-Drawer с вкладками (детали, файлы с версиями, AI-расходы, история), форма ТЗ с диалогом «без дедлайна», архив.
- Визуальная проверка агентом: скриншоты Playwright и перенос карточки реальной мышью; по скриншотам исправлены подпись колонки и ширина.
- **Независимый аудит — субагент** (параллельно основной агент писал backend аналитики): 4 средние находки — нельзя было отредактировать просроченную задачу, после 409 доска не обновлялась, при быстрых переносах терялись ошибки (особенность TanStack Query 5), Enter не открывал карточку. Всё исправлено, добавлены тесты.

## Этап 6. Аналитика

- Агент: агрегаты в PostgreSQL (загрузка, чистое время, просрочки по первой сдаче с атрибуцией первому сдавшему, AI-кредиты по сервисам и исполнителям, динамика по дням в таймзоне браузера), страница руководителя с графиками.
- Графики: палитра взята из скилла визуализации данных и **проверена его валидатором** на различимость при дальтонизме; рядом с каждым графиком — таблица с числами.
- Тесты сверяют каждое число с ручным расчётом на сценарии из 5 задач.

## Этап 7. Сид и демо-данные

- Агент: 20 сценариев задач, проигрываемых через бизнес-сервисы с подменой часов — история, отрезки работы и просрочки в демо настоящие. PNG-превью генерируются без сторонних библиотек.
- Проверено на живом стенде с нуля: сид при старте, сброс через CLI, скриншоты доски/карточки/аналитики.

## Этап 8. E2E и полировка

- Агент: два сквозных сценария Playwright (полный цикл задачи до аналитики; запрет брать свою задачу), e2e в CI на одноразовом стенде Docker Compose.
- По ходу e2e найдено и исправлено: показатели аналитики были неотличимы для скринридера (нет семантики) — добавлены role/aria-label. Проверена мобильная вёрстка (390 px).

## Этап 9. Деплой

- Агент: прод-надстройка Compose (наружу только 80/443, обязательные секреты), proxy с автоматическим выбором HTTP/HTTPS-конфига, продление сертификата, ночной сброс демо, инструкция.
- Проверено локально: `docker compose config`, `nginx -t` в обоих режимах (HTTPS — на самоподписанном сертификате), живой прогон proxy в сети стенда. Реальный выпуск сертификата требует домена — команды на сервере выполняет человек.

## Этап 10. Сдача

- Агент: README (соответствие требованиям ТЗ, тестовые пользователи, архитектура, решения, тесты, этот раздел), скриншоты на чистом демо, перенос документа решений в репозиторий.
- Финальная проверка: свежий клон репозитория → `docker compose up --build` на отдельных портах → e2e-сценарии против него.

## Ручная проверка фронта через Playwright (после сдачи)

- Агент прошёл интерфейс в живом браузере (Playwright MCP) за все роли: вход, взятие, сдача без результата, AI-расход, перенос на правки мышью, аналитика с периодами, пользователи, справочник, архив, 404, телефон.
- Найдено то, что не ловили unit- и e2e-тесты: календари Mantine показывали даты по-английски; карточки без доступных переносов были помечены `aria-disabled` (побочный эффект прошлого исправления); кнопки-крестики без подписи. Исправлено, добавлены регрессионные тесты; провайдеры вынесены в общий компонент, чтобы тесты проверяли ту же конфигурацию, что и приложение.

## Повторная сверка с ТЗ

- Агент заново сверил реализацию с текстом ТЗ построчно (по коду, а не по памяти). Нашлось буквальное расхождение: ТЗ требует референсы **в форме** постановки, а они добавлялись только после создания в карточке — теперь в форме есть ссылки и файлы. Плюс логика: из загрузки в аналитике пропадали задачи отключённого исполнителя; в карточке не было времени последней сдачи; «Готово» сортировалась по приоритету вместо свежести. Всё исправлено, тесты дописаны, e2e идёт по новой форме.

## Аудит по SOLID

- Агент проверил backend и фронт по SOLID; находки сначала записаны в документ, затем исправлены. Backend: сервис задач разделён на команды, чтение, журнал и отрезки работы; устранена обратная зависимость схем от сервисов; хранилище файлов больше не решает бизнес-политику и не знает про HTTP; исключения в правах доступа описываются данными. Фронт: страница аналитики разбита на компоненты секций, логика перетаскивания вынесена в хук, текст событий истории — реестр форматтеров.
- Где «канонический» слой был бы лишней сложностью (репозитории поверх ORM, классы-сервисы), это зафиксировано как осознанное решение, а не сделано ради формы.

## Правки аналитики: подвкладки

- План: агент задал вопросы по неоднозначностям (разбивка AI-расходов по кругам, состав вкладки времени, общие фильтры, кому засчитывать ожидание проверки) и записал план с решениями до начала кода.
- Агент: круг правок у AI-расхода (миграция с раскладкой старых записей по истории), три эндпоинта вкладок, ожидание в пуле и на проверке из истории статусов (оконная функция `LEAD`), вкладки на фронте с общими фильтрами и вкладкой в адресе.
- Проверка миграции: тест обнуляет круги на демо-данных, прогоняет SQL миграции и сверяет с кругами, записанными «вживую»; миграция прошла на существующей локальной базе.
- Визуальная проверка (Playwright, локальный стенд, десктоп и 390 px) нашла два дефекта вёрстки: плашки долей по сервисам упирались в край, на телефоне выбранная вкладка уезжала за экран — исправлено.
- Аудит (находки записаны до исправлений): список id задач передавался в SQL параметрами — при большом периоде упёрся бы в лимит asyncpg; заменено подзапросом. Давняя гонка в e2e (поиск поля «Оффер» до перехода на страницу) — первая гипотеза «холодный старт» оказалась неверной, причина найдена по error-context и исправлена.
- Рефакторинг: четыре независимых ревьюера (переиспользование, упрощение, эффективность, глубина решения); убраны дубли правила опоздания, лимита таблиц, ссылки на карточку; исправлена подпись вкладок для голосового управления (WCAG 2.5.3). Предложение убрать ожидание адреса в e2e отклонено как ошибочное.
- Повторный аудит (ревью на корректность): ошибка фонового обновления прятала данные вкладки; фильтр креативщика терял его время в переназначенных задачах; нижняя граница SQLAlchemy не соответствовала используемому API — исправлено, покрыто тестами.
